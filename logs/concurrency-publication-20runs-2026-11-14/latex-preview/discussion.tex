Table~\ref{tab:concurrency-correctness} reports 20 measured windows per configuration, collected across two sessions, with eight transactions per window. All operations use unsigned 16-bit modular arithmetic. With one writer, the canonical execution order always matched the planned submission sequence. With four writers, all 20 windows per platform were reordered in both modes. For \texttt{shared\_sum}, this did not change the final sum. For \texttt{shared\_ordered}, defined by $S\leftarrow 3S+x\pmod{2^{16}}$, every four-writer window produced a final state different from the result predicted by the planned submission sequence. Nevertheless, the verified per-request snapshots and final states matched replay in canonical blockchain order. These differences therefore reflect legitimate order-dependent execution rather than state inconsistencies.

No state mismatch was observed within the tested scope. This does not imply uninterrupted service availability: one Zama window failed its original retrieval audit and was validated separately afterwards, while a Fhenix preparation failure occurred before any request transaction was sent. Both historical attempts remain recorded. The results support correctness under the observed interleavings, but do not establish the absence of rare failures or correctness under arbitrary workloads. The eight requests within a window should not be treated as independent robustness trials.
